# MAGASIN Supervisor — Brain / Worker Multi-Conversation Architecture V1

**Date:** 2026-09-19  
**Status:** OWNER APPROVED / ACTIVE IMPLEMENTATION  
**Task:** TASK-049 — Supervisor Brain/Worker multi-conversation orchestration

## 1. Owner requirement

The Supervisor must support multiple concurrent ChatGPT work conversations without allowing uncontrolled chat creation or generic fixed-prompt continuation.

Canonical topology:

```text
Owner / repository source of truth
        ↓
ONE Brain conversation
        ↓ dynamic directives
Worker-1   Worker-2   Worker-3
   ↓          ↓          ↓
full completed response captured once
   └──────────┴──────────┘
        ↓
Brain conversation
```

The Brain is the only coordination conversation. Worker conversations execute bounded work assigned by the Brain.

## 2. Non-negotiable invariants

1. Exactly one active Brain conversation per Supervisor runtime generation.
2. Workers do not invent their next task. Every Worker instruction comes from a validated Brain directive.
3. The Supervisor must not repeatedly send one canned "continue" sentence to Workers.
4. A Worker result is captured only after the response is complete, as the full final assistant turn, exactly once per dispatched instruction.
5. Worker response bodies are transient in memory only. They may be relayed to the Brain but must not be persisted in Git, runtime status, diagnostics or logs.
6. Conversation targets and orchestration registry remain local-only.
7. Existing conversations are reopened/reloaded in place for ordinary recovery. Missing, stalled, unavailable or target-mismatch states never authorize a new conversation.
8. Rollover of an existing Brain/Worker conversation is authorized only when that exact conversation exposes a positive ChatGPT UI `conversationFull` signal.
9. Initial topology creation is a bounded bootstrap exception explicitly approved by the Owner:
   - one Brain conversation may be created when no Brain target exists;
   - new Worker slots may be created only from validated Brain `DISPATCH` directives;
   - active Worker count may not exceed the source-of-truth limit.
10. After bootstrap, no additional conversation may be created except:
    - a new Worker slot explicitly requested by the Brain within the configured worker limit; or
    - a rollover of a specific existing conversation whose UI has confirmed `conversationFull`.
11. Authentication, MFA, CAPTCHA, destructive/admin action and ambiguous decision states remain hard stops.

## 3. Five-Step decision

### QUESTION

The previous single-chat Supervisor conflated three responsibilities: reasoning, execution and recovery. It also used fixed continuation text and permitted rollover for missing/stalled/unavailable states. Those behaviors do not satisfy the Owner's multi-stream requirement.

### DELETE

Delete these behaviors from the active orchestration path:

- generic repeated continuation prompts as the task source;
- rollover on target-missing;
- rollover on conversation-missing;
- rollover after stall reload budget;
- rollover after unavailable reload budget;
- implicit adoption of unrelated ChatGPT conversations as a work target.

### SIMPLIFY

Use one Brain protocol and one Worker protocol:

- Brain decides and emits structured dynamic directives;
- Worker executes exactly one dispatched instruction at a time;
- Supervisor only transports directives/results and enforces safety/state.

### ACCELERATE

Multiple Workers may run simultaneously in separate ChatGPT tabs under the same dedicated Supervisor Chrome profile. The Supervisor polls them independently while ChatGPT continues generation in parallel.

Initial limit: **3 concurrent Workers**. The limit is source-of-truth configuration, not hard-coded business logic.

### AUTOMATE

Auto-upgrade from `main` may reinstall/restart the Supervisor only after CI passes and the source-of-truth mode is `BRAIN_WORKER_V1`. Runtime creation/recovery must remain fail-closed.

## 4. Brain directive contract

The Brain returns a machine-readable directive block:

```text
<<<MAGASIN_BRAIN_DIRECTIVE_V1>>>
{"actions":[
  {
    "type":"DISPATCH",
    "worker_id":"worker-1",
    "task_id":"TASK-049/A",
    "instruction":"Dynamic instruction generated by the Brain for this exact work item."
  }
]}
<<<END_MAGASIN_BRAIN_DIRECTIVE_V1>>>
```

Rules:

- `instruction` must be non-empty and is generated by the Brain from current context/source-of-truth.
- `worker_id` is stable across a Worker conversation generation.
- a `DISPATCH` to a new worker is allowed only while below `max_parallel_workers`;
- a `DISPATCH` to a busy worker is rejected/fail-closed;
- malformed directives do not trigger guessed work.

## 5. Worker result relay contract

After a dispatched Worker response is complete, the Supervisor captures the full final assistant turn once and relays it to the Brain with metadata:

```text
<<<MAGASIN_WORKER_RESULT_V1>>>
worker_id=worker-1
task_id=TASK-049/A
relay_id=<deterministic id>
turn=<conversation turn>
chars=<full response character count>

<full Worker response, untruncated>
<<<END_MAGASIN_WORKER_RESULT_V1>>>
```

Only `relay_id`, turn/count/status metadata may be persisted locally. The response body itself must not be written to disk/logs.

## 6. Rollover authorization matrix

| Condition | Reload/reopen same target | Create new conversation |
|---|---:|---:|
| `conversationFull=true` on exact target | optional | **YES** |
| target path temporarily not selected | YES | **NO** |
| target cannot be loaded | bounded retry/reopen | **NO** |
| conversation missing/unavailable | bounded retry then WAIT_USER | **NO** |
| response stalled | bounded reload then WAIT_USER | **NO** |
| network/transient error | bounded retry | **NO** |
| auth/MFA/CAPTCHA/security boundary | NO | **NO** |
| Brain asks for a new Worker slot and capacity exists | n/a | **YES — bootstrap/scale condition** |

A Worker/Brain rollover carries the same logical identity with incremented `generation`.

## 7. Local-only orchestration registry

Canonical local path:

```text
%LOCALAPPDATA%\MAGASIN\BusinessOS\supervisor\orchestration.json
```

It may store:

- Brain target pathname/generation;
- Worker target pathname/generation;
- Worker task/status;
- instruction/result hashes and turn ordinals;
- pending/relayed state.

It must never store:

- conversation bodies;
- Owner message bodies;
- Worker response bodies;
- credentials/cookies/tokens/secrets.

## 8. TASK-048 coexistence

TASK-048 remains a time-gated background night-run closure until 09:15 +07. Owner's explicit TASK-049 reprioritization must not be overwritten by that background hard-stop.

At the boundary, the hard-stop may mark the night window complete, but if `current_task != TASK-048` it must preserve the active Owner-selected task, autonomy and Owner boundary.

## 9. Acceptance

TASK-049 is complete only when tests prove:

- one Brain target and bounded Worker registry;
- dynamic Brain directives drive Worker messages;
- full Worker response captured once and relayed without persistence;
- at least two Worker conversations can be tracked concurrently;
- no rollover is returned for target-missing, conversation-missing, stall or unavailable states;
- rollover requires positive `conversationFull` evidence;
- initial Worker creation requires a validated Brain directive and capacity;
- hard-stop cannot overwrite an Owner-reprioritized TASK-049 state;
- auto-upgrade workflow installs Supervisor runtime changes from `main`;
- STOP/auth/MFA/CAPTCHA/destructive/admin boundaries remain fail-closed.
